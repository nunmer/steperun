# Site audit: steppe.run (2026-10-21)

Every public page was tested on the live site and checked against the code and
the database. The run analyzer (AI Coach) was left out on purpose.

## Summary

The site is slow because **nothing is cached and the database is slow**:

- Supabase answers even a trivial `select id limit 1` in **300–1100 ms**, from
  both US and EU (the TCP connect is about 2 ms). That's consistent with Disk IO
  budget throttling.
- **Every listing page misses the Vercel cache on every visit.** Only `/` and the
  legal pages are prerendered. `export const revalidate = 3600` has no effect on
  pages that read `searchParams` or have dynamic segments without
  `generateStaticParams`.

So every visit runs 2–4 queries at 0.5–2.5 s each. Fixing caching is the
biggest win. It also cuts Disk IO, which in turn makes the database faster.

| Page | Server time (uncached) | Cache |
|---|---|---|
| `/` | 1.1 s | HIT (prerendered) |
| `/rankings` | 3.0–3.9 s | MISS always |
| `/power-rankings` | 2.0–4.1 s | MISS always |
| `/events` | 1.7–2.0 s | MISS always |
| `/events/almaty_marathon_2026` | 2.5–3.3 s | MISS always |
| `/runners` | 0.9–1.2 s | MISS always |
| `/runners/[id]` | 1.3–1.6 s | MISS always |

Page weight is fine once compressed (15–19 KB over the wire), even though the
raw HTML is about 540 KB.

## Findings

Severity: 🔴 high · 🟠 medium · 🟡 low.

### Performance

1. 🔴 **No page-level caching on listing and detail pages.**
   - `/runners/[id]` and `/events/[slug]` have no `generateStaticParams`, so they
     are fully dynamic.
   - `/rankings`, `/power-rankings`, `/events`, `/runners` read `searchParams`,
     so they are fully dynamic too.
   - **Fix:**
     - Add `generateStaticParams` (empty list, or all 75 events) to the two
       dynamic-segment routes.
     - Wrap the read queries in `unstable_cache` (1 h, tag `results`).
     - Have the scraper workflow call a revalidate endpoint after an import.
2. 🔴 **Slow RPCs run on every visit:**
   - `get_rankings_all`: 2.5 s.
   - `get_distance_options`: 1.8 s (aggregates all 172k results).
   - `get_rankings_by_distance`: 1.5 s.
   - `get_event_stats`: 0.65 s.
   - **Fix:** cache their results (item 1). Optionally precompute distance
     options and rankings into a table during the scrape.
3. 🟠 **`/runners/head-to-head` queries both runners twice.** `getRunner()` is
   called in `generateMetadata` and again in the page, and it isn't wrapped in
   React `cache()`.
4. 🟠 **Event results sort about 17k rows per page.** Only `results(event_id)` is
   indexed, and the query orders by `distance_category, place`. **Fix:** a
   composite index `results(event_id, distance_category, place, id)`.
5. 🟠 **Redundant indexes raise write IO.**
   - `runners` has `idx_runners_elo` (defined twice in the SQL) and
     `idx_runners_elo_score_desc`, plus name, trgm, hidden, level, city and
     country indexes.
   - `results` has low-selectivity `idx_results_place` and
     `idx_results_category`.
   - Every ELO recalculation (52k rows updated today) writes to all of them.
     **Fix:** drop the duplicates and unused ones.
6. 🟠 **No `robots.txt` or sitemap.** Crawlers can walk every combination of
   ranking distance × year (129 distances), every `/runners?page=N` (about 2,800
   pages) and every power-ranking page. Each of those is an uncached DB hit.
   **Fix:** a `robots.txt` that disallows the query-string variants, plus a
   sitemap of the canonical pages.
7. 🟡 **Runner search (`/api/runners/search`, `/runners?q=`) is uncached.** It
   takes about 600 ms even with the trigram index. Results are 10 rows and could
   be cached for a few minutes per query.
8. 🟡 **Unused payload.** The event results query selects `checkpoint_times`,
   and nothing displays it.

### Lists that don't show everything

9. 🔴 **Pagination totals are estimates, so parts of lists are unreachable.**
   - Every list uses `count: "planned"`, a planner estimate.
   - Measured against exact counts:

     | List | Estimated | Actual |
     |---|---|---|
     | Power rankings, level 9 | 685 | 1,302 |
     | Power rankings, all | 84,263 | 85,313 |
     | Almaty Marathon 2026, all distances | 14,370 | 13,477 |
     | Almaty Marathon 2026, 10 km | 7,329 | 7,502 |

   - Level 9 therefore shows 23 pages instead of 44, so half the runners can't
     be reached. Elsewhere, "Next" leads to empty pages.
   - The level card and the pagination also disagree (1,302 vs 685).
   - **Fix:** exact counts, cached (see item 1). Or cheap exact counts from
     `get_elo_stats` / `events.total_results`.
10. 🔴 **The event distance filter is missing distances.**
    `get_event_categories_by_id` doesn't exist in the database, so the fallback
    reads the first 1,000 result rows. Almaty Marathon 2026 shows **2 of its 4
    distances**: 21 km and Nordic walking 10 km are missing. That affects every
    event with more than 1,000 results. **Fix:** add the RPC
    (`SELECT DISTINCT distance_category … WHERE event_id = $1`), or read the
    distances from `get_event_stats`, which the page already loads.
11. 🔴 **`/rankings` is capped at 100 rows with no pagination.**
    - "All" shows the top 39 of each of three distances.
    - A single distance shows the top 100.
    - Everyone below that can't be reached from the list.
    - The distance chips also show only 12 of 129 categories, so most trail
      distances can't be picked at all.
12. 🟠 **The sort order isn't unique, which risks repeated or skipped rows between
    pages.**
    - Power rankings sort by `elo_score` only, and up to 195 runners share one
      score.
    - `/runners` sorts by `full_name` only (duplicate names exist).
    - Event results sort by `place`.
    - No duplicates appeared in a 1,800-row sample, because Postgres happens to
      return a stable order, but nothing guarantees it. **Fix:** add `id` as the
      final sort key.

### Bugs

13. 🔴 **DNFs show as personal bests.**
    - On `/runners/[id]`, `toSeconds("--:--:--")` is NaN, so a DNF result stays
      "best".
    - **598** runner/distance pairs are affected. Live example: `/runners/12218`
      shows `--:--:--` as the 10 km PB.
    - DNFs also count towards "Races completed", and there are 20,331 DNF rows
      in total.
14. 🟠 **The "Previous" button on page 1 links to `page=0`.**
    - `<Button asChild disabled>` doesn't disable a `<Link>`. Affected:
      `/runners`, `/events/[slug]`.
    - `page=0` or `page=abc` produces a negative or `NaN` range, so the page
      renders empty with status 200.
    - **Fix:** hide the link on the edges, clamp `page` to 1…totalPages, and
      reject non-numeric values.
15. 🟠 **`/events` shows a "0" year group.** "Tour Of World Class Almaty" has
    `year = NULL` (its date is 2025-08-06). **Fix:** set the year in the data,
    and skip or label null years in the UI.
16. 🟠 **7 athletex events have no date.** Race Nation KZ 2025, Road Race Autumn
    2025/2026, Burabay Ice 2024/2026, Aqbura bay trail, Karkyra Ultra 2026. Their
    `.clax` date strings didn't parse, so the cards show no date and fall back to
    the autumn theme.
17. 🟠 **Unknown event slugs and runner IDs return 200, not 404.**
    `/events/nope`, `/runners/abc`. `notFound()` runs after streaming has started
    (because of `loading.tsx`), so the status is already 200. These are soft 404s.
18. 🟡 **Almaty Half Marathon 2023 has never been scraped** (`scraped_at` is
    NULL, 0 results).
19. 🟡 **Wrong hero copy.** The home page says "Every finish line — from 2015 to
    today", but the data starts in 2023.
20. 🟡 **Search ignores the other alphabet.** Searching "ivan" misses "Иван",
    and many runners are stored in Cyrillic. The folding in `scraper/names.py`
    could be applied to search too.
21. 🟡 **Events within a year are sorted by name, not date.**
22. 🟡 **Search wildcards aren't escaped.** A `%` or `_` typed in a search is
    treated as an `ilike` wildcard.
23. 🟡 **Config left over from Docker/Fly** in `next.config.ts`:
    `output: "standalone"` and `middlewareClientMaxBodySize: "100mb"`.

Every item except 17 is fixed. Migration `005` was applied the same day.

## Suggested fix order

1. **Caching** (items 1–3, 7). It's the biggest speed and Disk IO win.
2. **Correct lists:**
   - exact counts and unique sort keys (items 9, 12);
   - event distances (item 10);
   - rankings pagination and a better distance picker (item 11).
3. **Visible bugs** (items 13–17).
4. **IO hygiene:** robots.txt and sitemap, index cleanup, the composite index
   (items 4–6).
5. **Polish:** items 18–23.
